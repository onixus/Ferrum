# FERRUM — план развития

Статус: черновик. Ни одна строка этого документа не является утверждением
о том, что уже сделано; утверждения о сделанном живут в
[docs/MVP-1-BOUNDARY.md](docs/MVP-1-BOUNDARY.md) и держатся гейтом. Здесь —
что делать дальше и в каком порядке, с критерием закрытия у каждой фазы. Фаза
закрыта, когда закрыт её критерий, а не когда кончились силы.

## Исходная оценка

Инверсная зрелость: методологическая дисциплина уровня production при
интеграционной зрелости уровня прототипа. Компоненты и стык доказаны,
система — нет: ни один компонент не работал в живом кластере, admission не
принимал AdmissionReview от настоящего apiserver, controller не делал rollout,
агент не наполнял cgroup-индекс с настоящего kubelet.

Десять пунктов, по убыванию тяжести:

1. **TRL 4–5.** Система существует как манифесты, прошедшие lint, и стык,
   прошедший CI. Интеграционный слой apiserver ↔ webhook ↔ controller ↔ agent
   не исполнялся ничем.
2. **Реактивный enforcement.** Датапейс — tracepoint `sys_enter` + `SIGKILL`
   из userspace. `execve` к моменту сигнала завершился; это detect-then-kill,
   а не prevent. Индустрия (Tetragon, KubeArmor) на BPF LSM с синхронным
   `-EPERM`. RFC-02 это признаёт («LSM на pin path и in-kernel drop не
   реализованы»); признание не контрмера.
3. **TOCTOU на чтении пути.** Путь читается из user memory на `sys_enter` —
   double-fetch. Fail-closed на `path_unknown` закрывает нечитаемую страницу,
   не подменённую. Закрывается тем же LSM (п. 2): хук видит dentry, а не
   указатель.
4. **Fail-closed admission = риск доступности кластера.** Упавшие реплики
   webhook с `failurePolicy=Fail` останавливают создание pod'ов в scope.
   Сдвинулось 2026-08-31: HA-профиль есть — две реплики, PDB, который
   настоящий apiserver проверил отказом на втором eviction, мягкая
   anti-affinity, исключение `kube-system` по ключу, который проставляет
   apiserver, и заявленный числом бюджет латентности, который меряется
   гейтом. Там же нашлась и закрыта первая настоящая цена этого выбора:
   политика с `namespaceSelector` отказывала в каждом объекте уровня
   кластера, и живой FERRUM отвергал RBAC собственной переустановки.
   Сдвинулось ещё раз, тем же днём: blast radius описан числами из дерева
   (`docs/runbooks/README.md` §1, и каждое число сверяет гейт), а break-glass
   из threat model реализован — подписанный grant с обязательным окном не
   длиннее четырёх часов и хеш-цепочка журнала, где приостановление, которое
   некому записать, просто не вступает в силу. Не сдвинулось: один узел с
   обеими репликами по-прежнему возможен — anti-affinity мягкая, а на кластере
   с двумя узлами её никто не проверял; break-glass на живом кластере не
   прогонялся; и его журнал живёт в `emptyDir`, то есть долговечны только лог
   контейнера и метка на `/metrics`, обе вне контроля этого дерева.
5. **Нулевая интеграция с SOC.** Экспорт — JSONL на диск. Половина этого
   пункта сдвинулась 2026-08-31: `/metrics` есть у агента и у вебхука,
   `events_dropped_total` выведен наружу тем же значением, латентность
   admission меряется гистограммой, дайджест bundle едет меткой, причины
   деградации — метрикой с устойчивыми id, дашборд лежит в дереве и держится
   гейтом. Вторая половина сдвинулась там же: syslog/CEF/ECS есть, схема
   `EventEnvelope` версионирована и держится гейтом, сток подключён
   `overlays/siem-syslog`. Не сдвинулось: у стока нет TLS, и ни одна запись
   не доезжала ни до одного настоящего SIEM — приёмником во всех проверках
   был локальный сокет. Метрика говорит, что узел перестал enforce'ить; кого
   убили, теперь говорит запись, но только тому получателю, которого никто
   ещё не подключал.
6. **Все утверждения самозаверенные.** Jenkins локальный. 21 зелёная стадия —
   недоказуемое снаружи утверждение. Продукт про верифицируемость поставляется
   неверифицируемым. Сдвинулось на 2026-08-31 ровно то, что можно сдвинуть
   правкой дерева: `.github/workflows/ci.yml`, `.github/workflows/release.yml`
   и `SECURITY.md` в дереве есть. Не сдвинулось ничего из того, что требует
   исполнения: публичный CI не запускался ни разу, releases нет, в
   `ghcr.io/onixus/` пусто, ни одного SBOM никуда не приложено. Файл, умеющий
   опубликовать, и публикация — разные вещи.
7. **Матрица ядер не определена.** Два стенда уже дали два расхождения
   (aarch64 без `open`, Firecracker без module-tracepoint'ов). RHEL, Ubuntu
   LTS, Astra Linux SE не мерялись ничем.
8. **Позиционирование не сформулировано.** VAP/CEL — GA с 1.30 и частично
   дублирует admission-половину. Ответ (подписанные bundle, LKG, fail-closed,
   admission+runtime одной политикой, офлайн trust roots) существует, но не
   артикулирован ни в одном сравнении.
9. **GPL-3.0 не проговорена как выбор.** Self-hosted не мешает; embedding и
   dual licensing — мешает. Решение принять осознанно до первого внешнего
   контрибьютора. Развилка разобрана и **закрыта 2026-08-31: Apache-2.0** —
   раздел «Лицензия». Пункт снят.
10. **Bus factor = 1, пользователей 0.** Все допущения о нужных политиках и
    exception workflow — гипотезы, не проверенные ни одним deployment.

## Фаза 0 — существование доказуемо

Цель: внешний человек проверяет главные утверждения за 30 минут, не веря
ни одному слову README.

- E2E в kind/k3d: развернуть controller + admission + agent из `deploy/`,
  применить `prod-restricted.yaml`, прогнать приёмку §D RFC-02 против
  настоящего apiserver: unsigned image deny, privileged deny,
  `exec`+`/bin/sh` → kill, CP down → LKG. Каждый случай — именованный тест,
  цитируемый границей, как всё остальное.
- Публичный GitHub Actions для userspace-стадий (Format, Clippy, Test,
  Checks). Датапейсные стадии остаются на Jenkins — Actions настоящего ядра
  с tracefs не даёт, и зелёная стадия, не исполнившая attach, была бы тем
  самым гейтом, умеющим себя пропустить.
- Push образов в ghcr.io, подпись cosign, SBOM (cargo-auditable + syft) как
  release-артефакт. Продукт про подписанные bundle обязан поставляться
  подписанным.
- SECURITY.md, первый tagged release, решение по лицензии зафиксировано
  в этом документе. Состояние на 2026-08-31: `SECURITY.md` в дереве есть;
  тегированного релиза нет ни одного, и до его появления этот подпункт закрыт
  быть не может; решение по лицензии **принято 2026-08-31 — Apache-2.0**,
  раздел «Лицензия».
- Helm chart или kustomize overlay поверх `deploy/` — с гейтом
  устанавливаемости, как у самого дерева. Состояние на 2026-08-31: выбран
  kustomize (обоснование — `deploy/README`), `kubectl apply -k deploy` ставит
  контрольную плоскость, `overlays/mirrored-registry` переносит её в зеркало
  реестра, а гейт устанавливаемости — `install_gate.rs` — исполнен на kind
  на этой машине и стоит джобой `Install` в публичном воркфлоу, который не
  запускался ни разу. Не закрыто: DaemonSet агента в установку по умолчанию не
  входит — его Pod не стартует на узле без bpffs на `/sys/fs/bpf`, — так что
  «поставить всё одной командой» пока верно для плоскости управления, а не для
  продукта целиком.

Критерий закрытия: `git clone` → e2e зелёный на чистой машине с kind →
образ из ghcr верифицируется cosign'ом. Всё три — без доступа к локальному
Jenkins.

## Лицензия — Apache-2.0, решено 2026-08-31

**Вопрос поставлен и закрыт 2026-08-31 владельцем проекта: Apache-2.0.**
Дерево было под GPL-3.0-only; `LICENSE`, `[workspace.package] license` и
`deny.toml` приведены к новому выбору в тот же день. Ожидание от решения —
открытый канал встраивания и OEM: продукт можно взять как crate внутрь чужого
продукта, не открывая этот продукт целиком.

Смена ничьего согласия, кроме владельца, не потребовала: `deny.toml` разрешает
у зависимостей только пермиссивное (MIT, Apache-2.0, BSD-3-Clause, ISC, Zlib,
Unicode), то есть **ни одна зависимость не принуждала дерево к copyleft** — GPL
здесь был выбором, а не унаследованным обязательством, и весь копирайт
принадлежал одному человеку. Это же окно теперь закрыто в другую сторону:
выпущенное пермиссивно обратно под copyleft не возвращается, и на код, уже
взятый кем-то под Apache-2.0, никакое будущее решение не действует.

Про CLA: под Apache-2.0 он больше не нужен для той цели, ради которой
обсуждался. Dual licensing был единственным, что требовало права
перелицензировать чужие патчи, а пермиссивная лицензия этого рычага не
предполагает вовсе; входящие патчи по умолчанию приходят под той же
Apache-2.0 (§5), и DCO достаточно. Отдельного решения по CLA не принято, потому
что оно перестало быть нужным.

Разбор ниже оставлен как он был написан — он объясняет, чем платит выбранный
вариант, и не является юридической консультацией.

### Что было в дереве до смены

`LICENSE` — GPL-3.0, `[workspace.package] license = "GPL-3.0-only"`.

### Что GPL-3.0-only даёт и чего стоит

**Self-hosted поставка — не стоит почти ничего.** Обязательства GPL наступают
при *распространении* копии, а не при использовании. Оператор, поставивший
FERRUM в свой кластер и правивший его под себя, не распространяет ничего и не
должен ничего никому отдавать. Для целевого сегмента — закрытые контуры, где
продукт ставят себе, — GPL не создаёт трения вообще. (AGPL создаёт: она
достраивает обязательство до сетевого использования. Для плоскости, которая
работает *внутри* кластера получателя, а не предлагается как сервис, эта
достройка почти ничего не защищает — но пугает корпоративные юротделы заметно
сильнее.)

**Защита от «взяли и закрыли» — это то, за что GPL здесь платят.** Вендор,
собравший на этом коде проприетарный продукт и продающий его обратно, обязан
отдать исходники своей версии. Для проекта с bus factor = 1 это единственная
структурная защита от такого исхода.

**Встраивание (embedding) — закрыто, и это главная цена.** Rust линкует
статически; чужой продукт, подключивший `ferrum-policy` или `ferrum-agent`
как crate, получает производную работу и обязан выйти целиком под GPLv3.
Практически это значит: OEM-канал, поставка внутрь чужого дистрибутива
Kubernetes, встраивание в CNAPP или в аппаратный appliance — не состоятся.
Юротделы вендоров отказывают на этом раньше, чем читают код. Граница «отдельный
процесс через сеть или CLI» слабее и спорнее, но на неё нельзя опираться там,
где встраивание идёт crate'ом.

**Dual licensing — невозможен ни при каком CLA, если ждать.** Перелицензировать
код может только тот, кому принадлежит копирайт. Пока автор один — он может
выпустить то же дерево второй, коммерческой лицензией в любой момент. С первым
принятым внешним патчем копирайт становится долевым: без письменного согласия
каждого автора каждого патча второй лицензии не будет, и задним числом это
собирается плохо — люди меняют работу, почту и мнение.

**Датапейс добавляет ограничение со стороны ядра, а не лицензии.** BPF-программа,
вызывающая GPL-only-хелперы, обязана нести в объекте GPL-совместимую строку
`license`. Явной такой строки в `crates/ferrum-ebpf-progs` нет; чем она сейчас
проставляется и что с ней станет при смене лицензии дерева — надо проверить
**до** смены, а не после. Сейчас вопрос не стоит: GPL и там, и здесь.

### CLA и DCO — что это и почему без CLA дверь закрывается

Это два разных механизма, и путать их дорого.

- **DCO** (Developer Certificate of Origin) — подпись `Signed-off-by` в
  коммите. Контрибьютор утверждает, что имеет право отдать этот код под
  лицензией проекта. Дешёво, без бумаг, без юрлица, почти без трения.
  Владельцу проекта DCO **не даёт ничего сверх лицензии проекта**: копирайт
  остаётся у автора патча, и перелицензировать патч нельзя.
- **CLA** (Contributor License Agreement) — соглашение, по которому
  контрибьютор либо передаёт копирайт, либо (чаще) даёт владельцу проекта
  широкую лицензию с правом сублицензирования, в том числе на других условиях.
  Именно это делает dual licensing возможным позже. Цена: контрагентом по
  соглашению должно быть кто-то — человек или юрлицо; часть контрибьюторов
  отказывается из принципа; появляется администрирование, которого при bus
  factor = 1 не было.

Развилка тут ровно одна и она **односторонняя**: DCO сегодня и CLA завтра —
это CLA, который не покрывает патчи, принятые между сегодня и завтра. Поэтому
вопрос «CLA или DCO» решается до первого внешнего контрибьютора, а не после.
Пользователей и контрибьюторов пока ноль (п. 10 исходной оценки) — это и есть
единственное окно, когда решение бесплатно.

### Альтернативы и чем каждая расплачивается

| Вариант | Что даёт | Чем платит |
|---|---|---|
| **GPL-3.0-only** (было до 2026-08-31) | защита от проприетарного форка; self-hosted не задет; согласовано с GPL-миром ядра | нет OEM и встраивания; dual licensing только при CLA |
| **GPL-3.0-or-later** | получатель может перейти на будущие редакции FSF | отдаёт контроль над условиями будущей организации, которую владелец не выбирает |
| **AGPL-3.0** | закрывает SaaS-обход copyleft | для плоскости, работающей в кластере получателя, защищает почти ничего; отсекает больше корпоративных внедрений, чем GPL |
| **Apache-2.0** (выбрано) | максимальное распространение; встраивание и OEM открыты; явный патентный грант | вендор может закрыть и продавать обратно; обратной дороги нет — выпущенное пермиссивно не возвращается под copyleft |
| **MPL-2.0** | file-level copyleft: правки самих файлов FERRUM остаются открытыми, встраивание в проприетарный продукт разрешено | слабее GPL как защита; и как коммерческий рычаг почти ничего не даёт |
| **BSL / Elastic-подобная source-available** | сохраняет коммерческий рычаг без CLA | это **не** open source по OSI: закрывает CNCF, часть госзакупок и заметную долю контрибьюторов |
| **Open core** (GPL-ядро + проприетарные надстройки) | канал монетизации без смены лицензии ядра | надстройки, линкующие ядро, — производная работа, то есть всё равно нужен CLA; плюс постоянный спор «что в ядре, что в надстройке» |

### Что решено и чем за это заплачено

Выбран **Apache-2.0**. Дата — 2026-08-31. Ожидание — встраивание и OEM.

Заплачено ровно тем, что стоит в строке таблицы: вендор может взять дерево,
закрыть форк и продавать его обратно, и помешать этому больше нечем. Второй
вопрос — про CLA — снят: он имел смысл только как страховка dual licensing,
которого под пермиссивной лицензией не бывает.

## Фаза 1 — эксплуатируемость

Цель: SOC и SRE могут с этим жить.

- `/metrics`: events_dropped_total, admission latency histogram, bundle
  digest как label, degraded reasons. Grafana dashboard в дереве.
  Состояние на 2026-08-31: **сделано**. Отдельный crate `ferrum-metrics` без
  зависимостей (рендер + read-only `GET /metrics` на `std::net`), у агента —
  механический обход того же объекта, что печатает `status.json`, у вебхука —
  гистограмма латентности внутри `handle`, счётчики вердиктов и дайджест
  bundle. Порт опционален флагом, открыт манифестами, находим Service'ом и
  закрыт NetworkPolicy; дашборд — `deploy/observability/grafana-dashboard.json`,
  и расхождение с кодом роняет стадию `Security: metrics contract` в обе
  стороны. Живьём исполнено: бинарь агента отдаёт экспозицию на этой машине,
  вебхук — из Pod'а в kind, с настоящим `bundle_info{digest=...}`. Не сделано:
  метрик контроллера нет — он публикует `status.json` и порт не открывает, —
  и алертов на эти метрики в дереве нет ни одного.
- Событийный сток наружу: syslog/CEF минимум; схема `EventEnvelope`
  формализована как версионированный контракт для SIEM, нормализация
  написана для 2–3 систем.
  Состояние на 2026-08-31: **сделано, с одной названной дырой**. Схема
  называет себя сама (`schema` + `schemaVersion` в каждой записи, версия
  обязательна на чтении: отсутствующая версия — не «1.0»), правило эволюции
  записано, и держит его `Security: event contract` — инвентарь полей
  выводится сериализацией самого типа и сходится с замороженным
  `crates/ferrum-proto/schema/v1.0.json`, а записи прошлых версий
  декодируются этой сборкой. Нормализация: CEF 0 в кадре RFC 5424, RFC 5424
  со всей записью в SD-элементе, ECS одной JSON-строкой; сток — `ferrum-siem`,
  отдельный crate по образцу `ferrum-metrics`, `std::net`, без async-рантайма
  и TLS. Что уходит наружу — решение с причиной у каждого листа конверта;
  два человеческих имени с waiver'а не уходят. Недоступный SIEM учтён
  существующим `export_write_failed_total` и деградирует узел; второго
  счётчика не заведено. Живьём исполнено на этой машине: приёмка §D
  «`exec` + `/bin/sh` → kill» доехала до локального TCP-приёмника через
  поставляемую цепочку стоков, и UDP-приёмник получил CEF-датаграмму.
  Не сделано: **TLS у стока нет** — транспорт голый TCP или UDP, а запись
  несёт имена Pod'ов, namespace, процессов и политик; поставка отправляет
  оператора к локальному форвардеру, и это не то же самое, что решить задачу.
  Не сделано: обрамление RFC 6587 octet-counting (только LF), сток у вебхука
  (события enforcement пишет агент; вердикты admission наружу не едут),
  и ни один прогон на настоящем SIEM — приёмник во всех проверках был
  локальным сокетом, а не ArcSight, Elastic или Splunk.
- HA admission: 2+ реплики, PDB, anti-affinity, exempt kube-system через
  namespaceSelector. Latency budget заявлен числом и меряется бенчмарком
  в CI; p99, который не меряется, не заявляется.
  Состояние на 2026-08-31: **сделано, и одна находка починена по дороге.**
  Реплик две, `PodDisruptionBudget` с `maxUnavailable: 1` ставится тем же
  корнем kustomize, что и Deployment, anti-affinity по `hostname` — мягкая,
  и это выбор: `required` на одноузловом кластере (kind, куда ставят
  `install_gate.rs` и публичный воркфлоу) оставила бы вторую реплику в Pending
  навсегда. Исключение kube-system и `ferrum` решает
  `kubernetes.io/metadata.name` — ключ, который проставляет apiserver, а не
  метка, которую namespace выдал бы себе сам; декоративная
  `ferrum.io/webhook-exempt`, которую не читал никто, удалена. Бюджет —
  **5 мс на p99 `handle()`** для release-сборки (50 мс для отладочной, и это
  честность про артефакт, а не второй бюджет), меряется прогоном 10 000
  настоящих AdmissionReview в четыре потока, p99 читается из той самой
  гистограммы, которую вебхук отдаёт в `/metrics`, а число обязано быть
  границей корзины — интерполяция внутри корзины утверждала бы точнее прибора.
  Пропуска у гейта нет ни в каком виде. Измерено: release — среднее 34 мкс,
  p99 ≤ 0,1 мс; debug — 289 мкс и p99 ≤ 1 мс, на aarch64/macOS; в кластере
  один review — 135 мкс. Найдено и починено: политика с `namespaceSelector`
  закрывалась на любом объекте уровня кластера — apiserver не применяет
  `namespaceSelector` к таким ресурсам, они доезжали до вебхука, а тот
  спрашивал кеш меток о namespace, которого у них нет. Живой FERRUM отвергал
  RBAC собственной переустановки; теперь тот же apply принят, а bind на
  `cluster-admin` по-прежнему отвергнут — обе половины исполнены против
  настоящего apiserver. Не сделано: anti-affinity ни разу не проверялась на
  кластере с двумя узлами — на одном она по построению ничего не разносит;
  сквозная латентность, та, что видит `kubectl apply`, не меряна ничем; и
  стадия `Security: admission latency` на Jenkins и на GitHub не исполнялась
  ни разу.
- Break-glass из threat model реализован, с journal'ом. Runbook: webhook
  упал / агент degraded / bundle не грузится. Blast radius документирован.
  Состояние на 2026-08-31: **сделано, с одной границей, которая внешняя, и
  одной, которая нет.**

  Break-glass — `ferrum-breakglass`: подписанный в своём домене
  (`BREAK_GLASS_CONTEXT`, отдельном от домена подписи bundle) grant, который
  называет `subject`, `issuer`, `ticket`, `reason`, `issuedAt` и обязательный
  `expiresAt`; окно не длиннее четырёх часов, и бессрочный grant выразить
  нечем — поле не опционально, а потолок не предупреждение. Потолок туже, чем
  90 дней у `PolicyException`, намеренно: приостановление берут под давлением,
  без рецензии и без scope. Журнал — хеш-цепочка, в которую пишутся активация,
  истечение, отзыв и **отказ**; правка, удаление и перестановка ломают ссылку.
  Журнал, в который нельзя писать, не даёт grant'у вступить в силу, а
  армирование без писуемого журнала роняет старт процесса: аварийное
  отключение, не оставляющее следа, хуже отсутствия аварийного отключения.
  Само по себе это не новая возможность — `kubectl delete
  validatingwebhookconfiguration` работал и раньше и не оставлял в enforcement
  plane ничего; новым является след. Армирование — `overlays/break-glass`,
  отдельный намеренный apply; установка по умолчанию break-glass не включает.

  Не сделано, и обе половины названы там, где их прочтут. **Внешняя:** IdP.
  Проверка отвечает «держатель ключа K это утверждал»; что `subject` — живой
  уполномоченный человек, знает только система, выдающая ключи поимённо, и
  ставить её на путь нельзя — break-glass, падающий вместе с недоступным IdP,
  падает ровно в том отказе, ради которого есть. **Внутренняя:** файл журнала
  живёт в `emptyDir` и умирает с Pod'ом, потому что hostPath дал бы Deployment'у
  control plane право писать на узел, а PVC RWO не делится между двумя
  репликами; долговечны только две копии вне процесса — строка на stderr и
  голова цепочки меткой на `/metrics`, — и обе вне контроля этого дерева.
  Scope один, `admission`: роль `respond` у агента этим grant'ом не снимается.

  На живом kind прогнано, руками, один раз, и целиком: установка, армирование
  оверлеем, две реплики поставляемого образа, и все четыре события журнала —
  приостановление (privileged Pod, отвергнутый до grant'а, принят после, с
  warning'ом, несущим id grant'а и тикет), отзыв удалением Secret'а, отказ
  grant'у, подписанному ключом подписи bundle (один `rejected` при шестидесяти
  трёх подсчитанных отказах — заложенный обмен «журнал читаемый, счётчик
  полный»), и истечение двухминутного окна по часам без единой перезагрузки.
  Цепочку из шести записей подтвердил `ferrumctl verify-journal`.

  Тот прогон нашёл два дефекта, которых не видел ни один текстовый гейт.
  Процедура разбора журнала собирала логи обеих реплик в один файл, то есть две
  независимые цепочки, и проверка падала сообщением, которое читается как
  «запись пропала»; починено группировкой по `component` и гейтом на неё. И
  задержка вступления в силу оказалась не циклом опроса, а распространением
  Secret'а kubelet'ом — от пятнадцати до пятидесяти секунд; runbook теперь
  говорит «минуту», а не «секунду».

  Чего в прогоне не было: второго узла и кластера, у которого вебхук
  действительно не отвечает. И повторяемости: тестом держится ровно оверлей,
  само приостановление на живом кластере повторяется руками.

  Runbook'и — `docs/runbooks/README.md`: четыре отказа, радиус поражения,
  процедура break-glass и разбор инцидента. Четвёртый — «enforcement сняли» —
  единственный без симптома: пока self-watch вне процесса не построен, снятие
  enforcement на узле не наблюдаемо, и раздел говорит это первым абзацем
  вместо того, чтобы предлагать метрику, которой нет. Держит их за дерево
  `break_glass_gate.rs` по образцу `release_supply_chain`: каждый путь после
  `-k`/`-f` существует, каждое имя метрики публикует настоящий бинарь (набор
  получен рендером обоих бинарей), каждая причина деградации агента названа —
  и в обратную сторону тоже, — каждое число радиуса поражения равно
  константе, из которой взято, и граница про внешний IdP стоит дословно
  строкой из кода. Чего гейт не проверяет: что процедура помогает. Ни один из
  трёх runbook'ов не проходили целиком на живом кластере в состоянии отказа, и
  §7 документа говорит это первым абзацем.

  Радиус поражения описан числами из дерева: перехватываются CREATE/UPDATE
  `pods`, `rolebindings` (кроме `ferrum` и `kube-system`) и **всех**
  `clusterrolebindings` без исключений — apiserver не применяет
  `namespaceSelector` к объектам уровня кластера, поэтому пока вебхук не
  отвечает, не применяется и собственный RBAC FERRUM. Уже работающие Pod'ы не
  трогаются, DELETE не перехватывается — аварийный выход доступен всегда.
  Начало мгновенное, цена одного заблокированного запроса — до
  `timeoutSeconds: 5`; реплик две, PDB `maxUnavailable: 1`, anti-affinity
  мягкая, поэтому падение единственного узла забирает обе, и это названо
  остаточным риском. Вторая волна после восстановления — холодный кеш меток,
  на котором политика с `namespaceSelector` отказывает fail-closed.

Критерий закрытия: инцидент «respond убил не тот процесс» расследуется
из SIEM без доступа к ноде.

Состояние на 2026-08-31: **закрыт, и одной дырой по дороге меньше.**

Путь расследования пройден буквально, по тому, что действительно
экспортируется, и он упирался в булев `degraded`: запись говорила «узел был
деградирован» и не говорила чем, а «чем» жило в `status.json` — файле 0600 **на
узле**, то есть ровно за тем доступом, которого критерий требует не требовать.
А это не деталь: `lkg_partial` значит, что узел исполнял подмножество
подписанного снимка и `bundleDigest` называет больше правил, чем действовало;
`clock_rollback` — что waiver, который должен был понизить убийство, мог
прочитаться просроченным; `container_flag_disagreement`, `cgroup_index_empty`
и `identity_unknown` — что привязка cgroup→pod, на которой стоят `pod` и
`namespace` в записи, была системно ненадёжна.

Закрыто минорным поднятием схемы: `EventEnvelope` 1.1 несёт
`degradedReasons` — стабильные id, те же, что публикует
`ferrum_agent_degraded_reason`, а не переписываемые формулировки. Инвентарь и
записи 1.1 заморожены рядом с 1.0, записи 1.0 этой сборкой по-прежнему
декодируются, у поля есть решение с причиной в `ferrum_siem::FIELDS`, и все
три профиля его печатают.

Доказательство — исполненный тест, а не абзац:
`event_contract_gate.rs::the_wrong_process_investigation_is_answerable_from_one_exported_record`
берёт настоящее решение §D «`exec` + `/bin/sh` → kill», гонит его поставляемой
цепочкой стоков (`QueueSink` → `FanoutSink` → `SyslogSink`, профиль ECS) в
сокет и проходит разбор по одной пришедшей записи: что произошло, кого убили
(`tgid`, `pid`, `comm`), где (`node`, namespace, Pod), почему (`rule`,
политика), по какой выкатке (дайджест bundle — тот самый, который узел
проверил), насколько обоснованно (`labelsUnknown`, `pathUnknown`,
`containerUnknown`) и в каком состоянии был узел (`degradedReasons`, каждый id
— из таблицы самого агента). Ни `status.json`, ни `events.jsonl`, ни
`/metrics` тест не читает.

Чего в SIEM по-прежнему нет и это не мешает критерию: человеческие
формулировки причин (id хватает для вывода), `waiver.requestedBy` и
`waiver.approvedBy` — два имени, намеренно не выдаваемые наружу, потому что
`ticket` соединяет запись с системой, которая waiver выписала, — и свободные
тексты `terminalFault`, `containerMapError`, `respondDisabledReason`. Ничего
из этого не нужно, чтобы ответить «того ли убили»; всё это нужно, чтобы
исправить причину.

Чего это утверждение **не** говорит: приёмник во всех проверках был локальным
сокетом, а не ArcSight, Elastic или Splunk, и вердикты admission наружу
по-прежнему не едут — обе дыры остались с прошлого цикла и записаны в
«Не делает».

## Фаза 2 — превентивный enforcement

Цель: закрыть пп. 2–3 до того, как их покажут на демо.

- BPF LSM датапейс вторым режимом: `bprm_check_security` для exec,
  `sb_mount` для mount, `file_open` — синхронный deny вместо SIGKILL.
- Tracepoint-режим остаётся fallback'ом для ядер без `CONFIG_BPF_LSM`,
  с честным статусом деградации — по образцу существующих `DEG_`.
- Матрица ядер: RHEL 9, Ubuntu 22.04/24.04, Astra Linux SE. CO-RE, если
  его ещё нет; поведение на ядре без BTF названо, а не подразумевается.
- In-kernel rate limiting против syscall flood — контрмера из RFC-02 §C,
  которая сейчас существует только как строка таблицы.

Критерий закрытия: политика по exec на LSM-режиме предотвращает запуск
(`execve` возвращает `-EPERM`), и это исполнено на настоящем ядре тестом,
процитированным границей.

## Фаза 3 — рынок (параллельно, с фазы 1)

Цель: продукт понимает, кому он нужен.

Wedge — воздушный зазор: caller-supplied trust roots, ноль обращений в
Rekor/CT, офлайн PKI, LKG при потере CP. Это спроектировано для закрытых
контуров, и сегмент — КИИ/ГИС/ЗОКИИ, где SaaS-зависимые CNAPP не проходят
по модели поставки.

- Маппинг политик на Приказ ФСТЭК № 118 (требования к средствам
  контейнеризации) — тем же форматом, что CIS 5.x/MITRE в RFC-02.
- Сравнения «vs VAP/CEL», «vs Kyverno», «vs Tetragon» — честные, с колонкой
  «чего FERRUM не делает».
- Один дизайн-партнёр с закрытым контуром. Вход — observe-режим, respond
  выключен: низкорисковый пилот и есть продуктовая функция.

Критерий закрытия: один внешний deployment и один документ обратной связи
от него в дереве.

## Не делаем сейчас

- wasm-правила: ABI лежит, хост не развивается, пока фазы 0–2 открыты;
- UI/консоль;
- multi-cluster;
- сертификация ФСТЭК как процесс — дорого и рано. Архитектурные решения
  фаз 1–2 принимаются с оглядкой на неё: журналирование, контроль
  целостности, разграничение доступа.
